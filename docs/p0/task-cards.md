# P0 技术验证任务卡

依据：`docs/development-plan.md` v0.1。本文仅拆分执行工作，不改变原计划，不代表任何 P0 任务或 G0 已完成。所有任务初始状态均为“待执行”；完成须附构建、测试或实验记录。

## 排期与并行关系

| 时段 | 主线 | 可并行工作 |
| --- | --- | --- |
| 第一周 | P0-01 → P0-02 → P0-03 的单预设最小链路 | P0-08 在 P0-01 后启动；P0-06 在已有获授权 Serum 时可独立启动 |
| 第二周 | 完成 P0-03；随后启动 P0-04、P0-05、P0-07 | P0-04、P0-05、P0-07 共享 P0-03 后并行；P0-06、P0-08 同期收口 |

P0-01 是 P0-02、P0-08 的前置；P0-02 是 P0-03 的前置；P0-03 是 P0-04、P0-05、P0-07 的共同前置。P0-06 仅以前置条件“已安装获授权的 Serum”为依赖。第二周产出首批证据，完整 G0 验收仍按 3–4 周阶段执行。

## P0-01 范围与许可决策记录

- **目标**：锁定首发平台、开源/商业路线和组件、素材的许可边界，形成后续构建与分发约束。
- **输入/依赖**：无；需产品、集成及必要的许可审查参与。
- **允许产物范围**：范围与许可决策记录、组件及素材许可清单、未决问题与决策责任人；可记录首发平台建议及验证范围。
- **排除项**：不在证据不足时替用户决定开源或商业授权；不作法律结论；不承诺后续平台或功能。
- **执行步骤**：盘点 Vital、JUCE、Tracktion、测试预设/波表/采样及计划分发物；分别记录使用、修改、训练/推理、展示和再分发权利；列出路线选项、约束、阻塞项和待决策人；评审并冻结阶段适用版本。
- **验收条件**：首发平台和验证边界有记录；每个拟用组件及素材有来源、版本、许可状态与分发约束；开源/商业路线明确标为“已决定”或“待定”，待定项有负责人和截止门槛；闭源许可不可得时的降级路线已记录。
- **负责人角色**：产品 + 集成。
- **状态**：待执行。
- **安排/并行**：第一周优先完成；完成后解锁 P0-02、P0-08。许可路线若仍待定，不得把 P0-01 标记完成，但可在明确限制下进行不涉及分发的验证。

## P0-02 Vital 可重复构建

- **目标**：固定 Vital 源码提交、编译工具链和依赖，在干净 Windows 开发环境得到可重复构建的独立应用。
- **输入/依赖**：P0-01；选定 Vital 提交、Windows x64 工具链与依赖版本。
- **允许产物范围**：锁定文件、CMake/构建脚本、基础 CI、开发构建说明、独立应用构建产物及构建日志。
- **排除项**：不先做大规模 Vital 源码重构；不扩展正式 UI、插件功能或跨平台发布。
- **执行步骤**：固定源码提交和子依赖；记录编译器、SDK、生成器及配置；建立一键构建和基础启动检查；在干净环境复现并保存版本与日志。
- **验收条件**：文档化命令可从干净 Windows 环境成功构建；提交与依赖可追溯且未漂移；独立应用可启动；失败时给出可操作诊断。
- **负责人角色**：音频。
- **状态**：待执行。
- **安排/并行**：第一周，在 P0-01 后执行；完成后解锁 P0-03，可与已启动的 P0-06 并行。

## P0-03 无界面离线渲染接口

- **目标**：封装加载预设、设置参数、输入 MIDI 和离线渲染接口，提供可脚本化的无界面渲染 CLI。
- **输入/依赖**：P0-02；一个获授权测试预设、固定 MIDI/音符输入和渲染配置。
- **允许产物范围**：`core/audio/` 的最小引擎适配、`services/render/` 的离线任务、CLI 入口、接口草案、冒烟用测试输入与 WAV/日志证据。
- **排除项**：不实现网络或模型调用、完整 SoundSpec/ClipSpec、正式应用 UI、多轨时间线或实时回调中的文件 I/O。
- **执行步骤**：定义最小参数与错误模型；接入预设加载和 MIDI 事件；实现固定采样率/块大小的离线渲染；增加参数设置、缺失资源和取消/失败处理；用单预设贯通后扩展批量入口。
- **验收条件**：命令行可对指定预设和 MIDI 生成非空 WAV；参数修改可观察且输入配置写入日志；缺失或无效资源返回结构化错误；相同确定性输入可按约定容差重复渲染。
- **负责人角色**：音频。
- **状态**：待执行。
- **安排/并行**：第一周完成单预设链路，第二周完成批量 CLI；完成后 P0-04、P0-05、P0-07 可并行。

## P0-04 预设往返与资源验证集

- **目标**：建立预设保存/重载、外部资源处理和音频一致性的验证基线。
- **输入/依赖**：P0-03；至少 30 个获授权测试预设，覆盖调制、效果和外部资源。
- **允许产物范围**：`tests/fixtures/` 内获授权夹具、`assets/manifest/` 来源与许可记录、兼容矩阵、音频基线、验证脚本及结果记录。
- **排除项**：不纳入来源或再分发权利不明的素材；不把随机相位预设强行要求逐样本一致；不得默认测试音频可公开；发布前核实素材与输出的授权范围。
- **执行步骤**：选取并登记测试集；执行加载、渲染、保存、重载；区分确定性与随机源用例；记录缺失资源行为、特征容差和失败原因；整理兼容矩阵。
- **验收条件**：至少 30 个获授权预设完成往返验证；确定性用例满足音频一致性标准；随机用例固定随机源或通过已记录的特征容差；调制、效果、外部资源和缺失资源均有结果。
- **负责人角色**：集成 + 声音设计。
- **状态**：待执行。
- **安排/并行**：第二周在 P0-03 后启动，可与 P0-05、P0-07 并行；完整样本数可延续至 P0 第 3–4 周。

## P0-05 最小共享核心 VST3

- **目标**：使用 P0-03 的同一音频核心构建最小 VST3，验证播放、状态保存与恢复。
- **输入/依赖**：P0-03；目标 VST3 SDK/框架和计划中的 FL Studio、Cubase 验证环境。
- **允许产物范围**：`plugins/instrument/` 最小外壳、共享核心接入、插件构建配置、宿主加载/播放/状态恢复记录及独立版差异报告。
- **排除项**：不实现正式插件 UI、完整宿主同步、自动化体系、多实例服务或正式 P2 兼容承诺。
- **执行步骤**：构建最小插件外壳；接入共享核心和 MIDI/音频处理；保存并恢复最小状态；在两个目标宿主做扫描、加载、播放、工程重开；与独立版同状态渲染比较并解释差异。
- **验收条件**：两个目标宿主可扫描、实例化并播放；工程重开后最小状态恢复；独立版与插件渲染差异有测量和解释；崩溃、静音或状态丢失均有复现记录。
- **负责人角色**：音频 + 集成。
- **状态**：待执行。
- **安排/并行**：第二周在 P0-03 后执行，与 P0-04、P0-07 并行。

## P0-06 Serum 接口实验

- **目标**：验证 Serum 的加载、参数暴露、插件状态与原生预设保存路径，划清真实支持边界。
- **输入/依赖**：已安装且获授权的 Serum；明确版本与宿主环境。无此条件则保持阻塞事实，不推断能力。
- **允许产物范围**：接口实验报告、版本与环境记录、支持/不支持/未验证清单、插件状态样本和原生保存路径证据。
- **排除项**：不逆向或绕过授权；不把宿主状态改后缀冒充原生预设；不承诺无损转换或 P4 功能。
- **执行步骤**：记录版本与授权环境；验证实例加载及参数枚举/设置；比较宿主插件状态和原生预设的保存、重载路径；记录资源依赖与失败模式；按证据标记能力等级。
- **验收条件**：原生预设保存与插件状态保存差异明确；各候选能力标为支持、不支持或未验证并附证据；接口不足时记录“保留原插件手动使用、转换推迟”的降级方案。
- **负责人角色**：集成。
- **状态**：待执行。
- **安排/并行**：具备授权安装后可在第一周独立启动，第二周收口；可与 P0-02 至 P0-05、P0-07、P0-08 并行。

## P0-07 文本到音色闭环样例

- **目标**：用小型授权预设库跑通“文本检索 → 结构化修改 → 渲染试听”的命令行闭环。
- **输入/依赖**：P0-03；小型获授权预设库及来源记录；声音描述与受约束参数修改样例。
- **允许产物范围**：`services/ai/` 的检索/约束修改原型、授权小库索引、命令行样例、试听产物、评分与首轮听感问题记录。
- **排除项**：不以从零训练大型模型为依赖；不承诺任意音色匹配；不默认上传用户音频；不冻结 P1 声音类别或模型配置而缺少评估证据。
- **执行步骤**：登记授权小库；建立描述与可检索字段；实现检索候选和受范围校验的结构化修改；调用 P0-03 渲染并匹配试听响度；记录输入、候选、修改、耗时和人工反馈。
- **验收条件**：固定样例可重复完成完整链路并产出可试听结果；无模型或模型失败时可走预设检索降级；参数和资源引用经校验；有证据支持第二周检查点对 P1 声音类别与模型配置作后续决策，未定项继续标为待定。
- **负责人角色**：模型 + 声音设计。
- **状态**：待执行。
- **安排/并行**：第二周在 P0-03 后执行，与 P0-04、P0-05 并行。

## P0-08 时间线架构评估

- **目标**：比较 Tracktion 与自建轻量时间线方案的架构适配、许可和集成成本，为后续阶段形成决策记录。
- **输入/依赖**：P0-01；P1 单轨闭环、P2 插件复用和 P3 轻量工作站需求边界。
- **允许产物范围**：架构决策记录（ADR）、许可对比、能力/成本/风险矩阵、最小验证样例或测量记录、待定问题。
- **排除项**：不建设完整时间线或多轨 DAW；不因评估文档直接锁定供应商；不在许可路线待定时作不可逆架构承诺。
- **执行步骤**：定义比较标准；核对两方案的许可与分发影响；评估项目状态、音频图、插件宿主、时间线编辑和跨阶段复用；用最小样例验证高风险假设；记录推荐、反对理由及待定条件。
- **验收条件**：两方案按同一标准比较；许可、预计集成工作、核心耦合、P1–P3 影响和退出成本有证据；结论为已决策或明确待定，待定项有验证动作与责任人。
- **负责人角色**：应用 + 音频。
- **状态**：待执行。
- **安排/并行**：第一周在 P0-01 后启动，第二周形成首版 ADR；可与 P0-02 至 P0-07 并行。

## 共同记录要求

所有实验须记录基准机配置、采样率、缓冲大小、CPU、渲染耗时和缺失资源行为。第二周检查点应汇总可运行样例、构建说明、兼容性表、许可清单、性能记录和带证据的风险清单；这些产物只证明阶段进展，只有满足开发计划中的全部 G0 条件后才能判定 P0 通过。
