## 1. 产品目标与首版范围

SynthVerse 是语言驱动的合成器与轻量音乐工作站。用户通过文字描述声音，试听并修改可编辑音色，再生成适配该音色的 MIDI 乐句，最终导出预设、MIDI、音频或工程。产品提供独立应用与 DAW 插件，并支持外部 Agent 调用。

开发顺序：技术验证 → 独立版 MVP → 插件版 → 轻量工作站 → 高级预设兼容与音频反演。

第一版完整用户路径：

> 输入音色描述 → 试听三个候选 → 选择并用语言微调 → 生成八小节 MIDI → 锁定局部并修改 → 保存工程 → 导出 Vital 预设、MIDI 和 WAV。

首版明确包含：

- 基于固定版本 Vital 源码的内置合成引擎。
- 一个乐器轨、一个可编辑乐句、三个音色候选与基础 A/B 试听。
- 中文输入；内部使用稳定的结构化声音描述与音乐约束。
- 至少一个远程模型适配器、一个本地小模型配置，以及无需模型的预设检索降级路径。
- 用户自带 API Key；按能力检测模型，不假设所有接口均支持音频。
- 原生工程保存、撤销/重做、Vital 预设导入导出、MIDI/WAV 导出。
- 可被外部 Agent 调用的最小命令接口。

首版暂不承诺：任意声音无损合成、完整歌曲自动创作、Serum/Vital 无损互转、任意音频恢复原始参数、完整专业 DAW 功能、全平台同时发布。

## 2. 排期假设与团队

初始平台建议 Windows x64，插件优先 VST3，先验证 FL Studio 与 Cubase。macOS 独立版及 AU 作为后续发布范围；若首发必须包含 macOS，需增加构建、签名、音频设备与宿主验证工时。

排期以约 4 名全职工程师估算：音频/DSP 1 人、应用与交互 1 人、模型与分析 1 人、工程系统与集成 1 人；另需兼职声音设计、QA 和产品设计支持。角色可合并，但工期不会简单保持不变。单人开发不采用下表作为承诺。

| 阶段 | 预计周期 | 主要产物 | 阶段出口 |
| --- | --- | --- | --- |
| P0 技术验证 | 3–4 周 | 可构建引擎、离线渲染器、兼容性与授权决策记录 | G0：关键路径可行 |
| P1 独立版 MVP | 6–8 周 | 单轨创作闭环与最小 Agent 接口 | G1：端到端可用 |
| P2 插件版 | 4–6 周 | VST3、宿主同步与状态恢复 | G2：目标宿主稳定 |
| P3 轻量工作站 | 8–12 周 | 多轨、片段编排、混音与分轨导出 | G3：新手能完成短作品 |
| P4 高级兼容与反演 | 8–16 周以上 | Serum 集成、受限转换与实验性反演 | G4：按能力逐项发布 |

P0–P1 预计 9–12 周，至 P3 累计约 21–30 周，尚未包含发布缓冲。建议各里程碑额外预留约 20% 的集成与修复空间。P4 是研究性预算区间，不能据此承诺完整转换效果。

Serum 的接口与授权风险在 P0 提前验证，其完整集成仍放在 P4。P0 同时做最小插件构建验证，以免到 P2 才发现核心无法复用。

## 3. 架构基线

### 3.1 共享核心与执行边界

- **音频核心**：C++，封装 Vital 引擎，负责 MIDI、参数、效果和确定的音频渲染行为。
- **应用外壳**：评估 JUCE，用于独立应用和 VST3；不在 UI 中直接实现业务状态。
- **项目核心**：统一 SoundSpec、ClipSpec、Project、命令事务和撤销系统。
- **AI 工作进程**：语言解析、检索、音频分析、参数搜索与候选排序；开发期可用 Python。
- **后台渲染**：独立于实时演奏实例，有并发与 CPU 预算；任务可以取消。
- **适配层**：按引擎和版本读写预设，保留原生状态及引擎专有字段。
- **自动化接口**：UI、内部规划器与外部 Agent 共用命令，MCP 作为接口适配层。

实时音频回调不得执行网络访问、模型推理、文件 I/O、阻塞锁等待或不可控内存分配。后台任务提交经过校验的状态，在安全边界切换，并对连续参数做平滑处理。

### 3.2 核心数据对象

| 对象 | 必要内容 |
| --- | --- |
| SoundSpec | 引擎与版本、参数、调制、资源引用、声音描述、宏控制、原始预设/状态 |
| ClipSpec | 音符、时序、力度、控制信息、速度/调性上下文、锁定区域 |
| Project | 轨道、片段、混音、自动化、资源清单、格式版本、保存状态 |
| GenerationRecord | 输入约束、模型标识、种子、候选、评分、已接受结果、预算与耗时 |
| Job | 任务 ID、状态、进度、取消标记、结果引用、结构化错误 |

工程重开读取已保存结果，不重新调用模型。资源使用内容哈希识别；API Key 只保存系统凭据引用。对外导出时单独处理资源的再分发权限。

### 3.3 建议代码布局

```text
apps/standalone/        独立应用
plugins/instrument/     插件外壳
core/audio/             引擎适配与实时音频
core/project/           工程、命令、撤销与版本迁移
services/ai/            模型适配、规划与生成
services/render/        离线渲染任务
adapters/presets/       Vital、后续 Serum 适配
interfaces/agent/       命令协议与 MCP 适配
assets/manifest/        资源来源与许可清单
tests/fixtures/         获授权的预设、MIDI 和音频测试素材
docs/                   产品、架构、兼容矩阵与发布文档
```

此布局为实施建议，P0 根据 Vital 的构建耦合情况调整，避免先进行大规模源码重构。

## 4. P0：技术验证（3–4 周）

目标：确认声音引擎、预设、共享核心与商业路线可行，建立后续工作的真实基线。

| 编号 | 任务 | 负责人角色 | 依赖 | 交付物 |
| --- | --- | --- | --- | --- |
| P0-01 | 锁定首发平台、开源/商业路线和组件许可范围 | 产品 + 集成 | 无 | 范围与许可决策记录 |
| P0-02 | 固定 Vital 源码提交、编译工具链与依赖 | 音频 | P0-01 | 可重复构建脚本、独立应用 |
| P0-03 | 封装加载预设、设置参数、输入 MIDI、离线渲染接口 | 音频 | P0-02 | 无界面渲染 CLI |
| P0-04 | 建立预设保存/重载与资源依赖验证集 | 集成 + 声音设计 | P0-03 | 兼容矩阵、音频基线 |
| P0-05 | 用同一核心构建最小 VST3，验证播放与状态恢复 | 音频 + 集成 | P0-03 | 插件技术样例 |
| P0-06 | 验证 Serum 的加载、参数暴露、状态与原生保存路径 | 集成 | 已安装获授权的 Serum | 接口实验报告、支持/不支持清单 |
| P0-07 | 用小型授权预设库验证文本检索、结构化修改与试听 | 模型 + 声音设计 | P0-03 | 闭环命令行样例 |
| P0-08 | 评估 Tracktion 与自建轻量时间线方案 | 应用 + 音频 | P0-01 | 架构决策记录、许可与集成成本 |

G0 验收：

- 在干净的 Windows 开发环境中按文档成功构建。
- 至少 30 个获授权测试预设完成加载、渲染、保存、重载；包含调制、效果和外部资源情况。
- 确定性预设验证音频一致性；随机相位等预设固定随机源或比较特征容差，不强求逐样本一致。
- 独立版与最小插件对同一状态的渲染差异得到解释和记录。
- 明确 Serum 原生预设保存与插件状态保存的差异；无法验证的能力不进入发布承诺。
- 记录基准机配置、采样率、缓冲大小、CPU、渲染耗时和缺失资源行为。

停止/降级条件：若无法获得适用的闭源许可，选择合规的开源路线或重新评估引擎；若 Serum 自动化接口不足，保留原插件手动使用方案，转换功能推迟。授权问题与核心引擎可行性是 G0 必须解决的阻塞项。

## 5. P1：独立版 MVP（6–8 周）

目标：完成单轨、八小节、可编辑且可保存的创作闭环。

### 5.1 实施包

| 编号 | 任务 | 关键实现 | 依赖 |
| --- | --- | --- | --- |
| P1-01 | 工程与命令系统 | SoundSpec/ClipSpec、撤销/重做、原子保存、格式版本 | G0 |
| P1-02 | 预设索引与特征库 | 多音高/力度渲染、包络/频谱特征、资源来源记录 | P0-03 |
| P1-03 | 模型适配 | 远程与本地适配器、结构化输出校验、超时/取消、凭据存储 | P1-01 |
| P1-04 | 语言设计音色 | 意图解析→检索→受约束修改→渲染→排序；输出三候选 | P1-02、03 |
| P1-05 | 音色感知的 MIDI 生成 | 速度/调性/长度/风格约束、动机扩展、音域与密度调整 | P1-01、02、03 |
| P1-06 | 新手交互 | 试听、A/B、宏控制、钢琴卷帘、锁定局部、生成进度 | P1-01、04、05 |

| P1-09 | 端到端验证 | 音频稳定、失败恢复、凭据隔离、用户任务测试 | P1-06、07、08 |

### 5.2 范围控制

- 初期使用有来源记录的预设与合成模板；不把从零训练大型模型列为依赖。
- 先支持少量明确标注的声音类别，如 bass、lead、pluck、pad；测试单独统计各类表现。
- 先支持三类明确的风格模板，覆盖节奏密度、切分和情绪差异；具体曲风在 P0 声音测试中定稿。
- 小模型负责意图与受约束编辑；包络、频谱、峰值和响度分析使用本地 DSP。
- 每个任务限制候选数、迭代轮数、耗时和费用；用完预算返回最佳可用结果或明确失败原因。
- 候选比较采用试听响度匹配，保留原始渲染文件。

### 5.3 G1 验收

功能与可靠性为硬门槛：

- 在无需开发工具的环境完成安装和完整用户路径。
- 断网可重新打开工程并播放、编辑、导出；已安装本地模型时可执行声明支持的本地任务。
- 模型超时、异常结构化输出或进程退出不导致播放中断和工程丢失。
- 锁定区域在局部修改后保持不变；所有用户接受的生成修改可撤销。
- 导出的 Vital 预设在声明支持的目标版本中正确加载；MIDI 在目标 DAW 中保持时序。
- 工程与日志不含明文 API Key；未授权上传的音频不离开本机。
- Agent 重试不会重复新增对象；项目版本冲突会明确返回错误。

体验目标为暂定指标，P0 建立基线后冻结：

- 固定至少 40 条音色请求和 20 条旋律任务，由至少 3 名评估者盲听。
- 至少 70% 的音色请求在前三个候选中有一个被多数评估者认为符合核心描述；按声音类别报告结果。
- 至少 8 名无专业 DAW 经验的试用者中，6 名可在 15 分钟内独立导出八小节作品。
- 在公开记录的参考硬件和模型配置上，预设检索预览目标 P95 ≤ 3 秒，完整生成目标 P95 ≤ 60 秒；远程与本地分别报告。
- 在约定音频负载下连续运行 30 分钟并同时执行生成任务，无可归因于模型调度的音频丢帧；记录声卡和缓冲配置。

若体验目标未达成，优先缩小支持声音/风格范围或改善候选库，不以增加模型规模作为默认解决方案。

## 6. P2：DAW 插件版（4–6 周）

目标：共享 P1 核心，在宿主中稳定执行音色与乐句工作流。

主要任务：

1. 实现 VST3 正式外壳、稳定参数 ID、宏控制和宿主自动化。
2. 跟随宿主速度、拍号、播放/停止、循环和位置跳转；防止插件与宿主双重播放。
3. 明确 MIDI 输入、内部乐句播放及 MIDI 输出模式；宿主不支持便利路由时提供文件拖出。
4. 完成插件状态保存/恢复、资源定位与缺失提示，不把 API Key 写入宿主工程。
5. 实现多实例的 AI 服务复用与资源限额；每个实例保持独立项目上下文。
6. 区分快速离线导出与实时播放，处理尾音、延迟报告和采样率切换。
7. 支持 MIDI/WAV 拖出；插件窗口关闭后仍正常播放，重新打开恢复 UI。
8. 建立 FL Studio、Cubase 的明确版本矩阵与插件验证流程。

G2 验收：

- 两个目标宿主均通过扫描、加载、工程保存/重开、离线导出和自动化测试。
- 覆盖 44.1/48/96 kHz，64/128/512 等代表性缓冲配置；性能目标按配置分别报告。
- 覆盖跳转、循环、变速、停止、挂起恢复、界面关闭、多实例和服务失联。
- 保存工程后的音色、MIDI、宏参数和资源恢复正确。
- 不支持的宿主能力在界面说明，不用“支持 VST3”替代宿主级验收。

## 7. P3：轻量音乐工作站（8–12 周）

目标：用户无需专业 DAW，即可完成一首约 1–3 分钟的短作品。

实施顺序：

1. **多轨与片段**：先支持约 8 轨的明确性能目标、片段复制/裁切/循环、静音/独奏和吸附。
2. **编曲结构**：前奏、主段、过渡等段落操作，和声上下文共享；生成只作用于选定范围。
3. **基础声部**：旋律、低音、和弦和鼓轨；鼓使用有授权的采样或内置生成方式。
4. **基础混音**：音量、声像、基础效果、发送与自动化；共享同一套工程命令。
5. **资源与性能**：冻结轨道、恢复可编辑状态、资源打包、缺失处理、峰值保护。
6. **导出**：整曲 WAV、分轨 WAV、分轨 MIDI，统一起点与尾音策略。
7. **恢复与迁移**：自动保存、崩溃恢复、工程格式迁移和安装包升级验证。

G3 验收：

- 新手能从模板开始编排并导出完整短作品，无需理解复杂总线和专业路由。
- 指定参考工程在基准硬件上达到目标轨数，播放、冻结与导出结果符合记录的容差。
- 分轨文件起点一致，尾音完整，重新导入可对齐。
- 在另一台机器恢复已打包且许可允许携带资源的工程；缺失插件或资源有可操作提示。
- P1/P2 工程在升级后仍可打开，旧版本行为通过迁移测试保留。

本阶段不扩展到复杂录音棚路由、视频同步、全面乐谱排版或专业母带系统。

## 8. P4：高级兼容与音频反演（8–16 周以上）

目标：按风险分批发布，不把所有能力合并成“万能预设转换”。

| 子阶段 | 能力 | 实现与验收 |
| --- | --- | --- |
| P4-A | Serum 原插件使用 | 使用用户授权安装；隔离扫描与渲染；验证版本、资源及工程恢复 |
| P4-B | 指定 Serum 目标生成 | 在已验证的参数/状态接口上生成；原生预设必须由目标 Serum 成功加载 |
| P4-C | Vital/Serum 受限转换 | 从简单振荡器、包络、基础调制子集开始；逐项列出近似和不支持项 |
| P4-D | 单音音频转预设 | 固定目标引擎，多音高/力度重建验证，比较包络、频谱与听感 |
| P4-E | 乐句与混合音色 | 再评估分离、采样补充、混合引擎；作为独立研究范围 |

转换流程：解析原始状态或渲染参考 → 建立目标能力约束 → 参数映射/检索初始化 → 搜索优化 → 在多音高与力度上渲染 → 输出预设及转换报告。

G4 按子能力验收：

- 原生预设导出与宿主状态导出明确区分，不能更改后缀冒充成功。
- 比较使用响度匹配与统一测试乐句，并单独测未参与优化的音高和力度。
- 盲听结果、支持特征、适用音域与失败案例共同形成发布说明。
- 不支持的滤波器、效果、调制或采样功能明确标记；必要时提供音频/采样替代产物。
- 若转换听感或性能未达目标，发布为实验功能或继续限制子集，不宣称无损兼容。

## 9. 质量、数据与安全贯穿项

| 类别 | 实施要求 |
| --- | --- |
| 构建 | 锁定依赖与引擎提交；CI 构建、打包、基础启动与渲染冒烟验证 |

## 10. 风险与应对

| 风险 | 最早验证 | 应对 |
| --- | --- | --- |
| Vital 开源版本与用户预设版本不一致 | P0 | 固定支持矩阵，保留原始文件；必要时使用匹配版本插件 |
| GPL/商业授权与产品路线冲突 | P0 | 在分发前明确路线，记录组件及素材许可 |
| Serum 接口或格式无法可靠写入 | P0 | 优先原插件播放与目标内设计；原生导出单独设门槛 |
| 音色语义匹配效果不足 | P0–P1 | 缩小声音类别、改善库与描述、结合 DSP 和人工盲听 |
| 小模型结构化输出不稳定 | P1 | 约束解码/校验、有限重试、检索和规则降级 |
| 推理挤占实时音频资源 | P0–P2 | 进程隔离、低优先级、并发限制与冻结缓存 |
| 插件宿主行为差异 | P0、P2 | 尽早最小样例，逐宿主明确验收 |
| DAW 范围膨胀 | P3 | 以短作品任务为边界，功能逐项验收 |
| 反演只拟合一个音符 | P4 | 多音高/力度训练与留出测试，报告适用范围 |

## 11. 首两周执行清单

第一周：

- 完成 P0-01 范围与许可记录，确认开发环境和可使用的测试素材。
- 固定 Vital 提交并完成第一份可重复构建。
- 创建 CMake/构建脚本、基础 CI 与开发说明。
- 验证一个预设的加载、MIDI 播放与 WAV 渲染。
- 定义 SoundSpec、ClipSpec 和引擎适配接口草案。

第二周：

- 完成无界面批量渲染 CLI 与首批预设往返测试。
- 构建共享核心的最小 VST3，并在两个宿主做初步加载验证。
- 执行 Serum 接口实验，记录真实能力和缺口。
- 用授权小库跑通“文本检索→参数修改→渲染试听”样例。
- 记录基准性能与首轮听感问题，决定 P1 支持的声音类别与模型配置。

两周检查点交付：可运行样例、构建说明、兼容性表、许可清单、性能记录和带证据的风险清单。未通过 G0 前，不进入完整 UI 与多轨 DAW 开发。

## 12. 里程碑交付与维护规则

每个里程碑交付安装包或可运行构建、演示工程、验收结果、已知限制和下一阶段排期修订。功能完成以验收通过为准，不以代码合并或界面出现为准。

阶段内按周演示一条真实用户路径。每阶段结束更新兼容矩阵和风险清单；新增功能必须明确替换现有范围或增加工期。阶段工期按性能和听感验证结果调整。
